Caching in System Design

An End-to-End Visual Guide to Performance Optimization

1. The Fundamentals

What is Caching? A cache is a high-speed data storage layer that stores a subset of data, typically transient in nature, so that future requests for that data are served up faster than accessing the data's primary storage location.

Why Cache?

  • Reduce Latency: Memory (RAM) access is orders of magnitude faster than Disk (SSD/HDD) or network access.
  • Reduce Load: Protects backend databases from being overwhelmed by heavy read traffic.
  • Cost Efficiency: Cheaper to serve repeated requests from a cache than to scale up expensive databases.

Key Metrics

  • Cache Hit Ratio: (Hits / Total Requests). You want this as close to 100% as possible.
  • Latency: Time taken to fetch data.
  • Throughput: Number of requests served per second.

2. Where Do We Cache? (Caching Layers)

Caching is not just for the database. It happens at almost every step of the network request journey.

1. Client / Browser Cache (Local Storage, HTTP Cache-Control)
2. Edge / CDN Cache (Cloudflare, Akamai - caches static assets globally)
3. API Gateway / Load Balancer Cache (Reverse Proxies like Nginx, Varnish)
4. Application Local Cache (In-memory: Guava, Caffeine, ConcurrentHashMap)
5. Distributed Cache (Redis, Memcached - shared across app servers)
6. Database Query Cache (Internal DB mechanisms like Buffer Pool)

5. Eviction Policies

Cache memory is limited. When it gets full, older data must be removed to make room for new data.

Policy Description Best Use Case
LRU (Least Recently Used) Discards the item that hasn't been accessed for the longest time. General purpose web traffic, news feeds.
LFU (Least Frequently Used) Discards the item accessed the fewest number of times. Static configurations, dictionaries.
FIFO (First In, First Out) Evicts the oldest data added to the cache, regardless of access. Time-series data, logs.
TTL (Time To Live) Data expires automatically after a set time limit (e.g., 5 minutes). Session data, ephemeral tokens, dynamic pricing.

6. Common System Pitfalls & Mitigations

1. Cache Penetration (Cache Miss Storm)

Problem: A client requests data that doesn't exist in the cache OR the database. The request bypasses the cache, hits the DB, fails, and repeats. Malicious users can exploit this to crash the DB.

Solution:
1. Cache null/empty values (with short TTLs).
2. Implement a Bloom Filter before the cache to rapidly check if a key even exists.

2. Cache Avalanche

Problem: A large number of cache keys expire at the exact same time, sending a massive wave of read requests to the database simultaneously.

Solution: Add a random jitter (randomized offset) to your TTLs. Instead of expiring everything at exactly 60 minutes, expire them between 55 and 65 minutes.

3. Thundering Herd (Dogpile Effect)

Problem: A highly popular key (e.g., a viral tweet) expires. Thousands of concurrent requests hit the cache simultaneously, find a miss, and ALL query the database at the same time to regenerate the cache.

Solution: Use a Mutex Lock / Distributed Lock. Only the first thread that misses gets the lock to query the DB. Other threads must wait a few milliseconds and check the cache again.

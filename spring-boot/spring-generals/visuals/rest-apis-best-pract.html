REST API Best Practices

A comprehensive guide to designing scalable, maintainable, and predictable APIs.

1 Stateless APIs

Deep Dive:

The "ST" in REST stands for State Transfer. A purely stateless API means that the server retains absolutely no memory of the client's past requests. Every single HTTP request sent from the client to the server must contain all the information necessary for the server to understand and process it. The server does not rely on a "session" stored in its memory.

Why is this crucial? Scalability. If server A holds a user's session, the load balancer must always route that user to server A (sticky sessions). In a stateless architecture, any server in a massive cluster can process any request at any time, allowing you to instantly scale up or down based on traffic.

💡 Tips & Tricks

  • Use JWTs: JSON Web Tokens are the industry standard for stateless authentication. The client stores the token and sends it via the Authorization: Bearer header. The server simply validates the token's cryptographic signature without checking a session database.
  • Cache Aggressively: Because requests are stateless and standalone, GET requests become highly cacheable by CDNs (like Cloudflare or AWS CloudFront), drastically reducing database load.

2 HTTP Verbs for CRUD Operations

Deep Dive:

REST is "Resource-Oriented." You expose resources (nouns) and manipulate them using standard HTTP methods (verbs). You should never use verbs in your URLs (e.g., avoid /createNewUser). Instead, use the HTTP protocol as it was intended:

  • POST Create: Adds a new resource to a collection.
  • GET Read: Retrieves a resource or collection. Must never change server state.
  • PUT Update (Replace): Replaces the entire resource with the payload.
  • PATCH Update (Modify): Partially updates a resource (only changes provided fields).
  • DELETE Delete: Removes a resource.

💡 Tips & Tricks

  • Embrace Idempotency: GET, PUT, and DELETE must be idempotent. This means making the same request once or 100 times should leave the server in the exact same state. (e.g., Deleting an already deleted record shouldn't crash; it should return a 204 No Content or 404 Not Found).
  • POST vs PUT: Use POST when the server decides the ID of the new resource. Use PUT if the client defines the ID (e.g., PUT /files/my-document.pdf).

3 Use Parameterized URIs for Identity

Deep Dive:

URIs (Uniform Resource Identifiers) should uniquely identify a specific resource. To fetch, update, or delete a specific item, the identity of that item should be embedded directly into the URI path as a parameter.

✅ GOOD: GET /users/123
❌ BAD:  GET /users?id=123 (Don't use query params for primary identity)

This creates a logical, hierarchical structure. If resources have relationships, the URI should reflect that parent-child relationship.

💡 Tips & Tricks

  • Keep Nouns Plural: Always use plural nouns for collections. Use /users/123, not /user/123. It reads naturally: "Get id 123 from the users collection."
  • Limit Nesting Depth: Avoid deeply nested URIs. /users/1/orders/5/items/10 is too deep and ties your API directly to your database schema. Limit nesting to one or two levels (e.g., /users/1/orders). If you need an item, access it directly via /items/10.
  • Use Hyphens for multi-word resources: /user-profiles/123 is standard; avoid camelCase or underscores in paths.

4 Query Params for Additional Options

Deep Dive:

While path variables (/users/123) dictate identity, query parameters (?key=value) dictate options on a collection. Query parameters should be used exclusively for modifying the results of a GET request. The main use cases are Filtering, Sorting, Searching, and Pagination.

GET /products?category=electronics&sort=price_desc&limit=20&offset=40

By keeping options in the query string, you keep your base URIs clean and prevent parameter explosion in your routing logic.

💡 Tips & Tricks

  • Mandatory Pagination: Never return an entire database table. Always implement default pagination limits (e.g., default limit=50) to protect your server from memory exhaustion.
  • Consistent Naming: Stick to a single naming convention for query params. Standardize on snake_case (e.g., created_after) or camelCase (e.g., createdAfter), but do not mix them.
  • Complex Queries: If a query becomes incredibly complex with dozens of parameters, consider using a POST request to a search endpoint (e.g., POST /products/search) where the complex query is placed in the JSON body.

5 API Versioning

Deep Dive:

Once your API is published and consumed by mobile apps or external partners, it becomes a strict contract. You cannot make "breaking changes" (like renaming a field, removing an endpoint, or changing data types) without crashing the clients relying on it.

API Versioning is how you maintain stability and predictability. By versioning your API, you can introduce a new v2 with structural changes while v1 remains active, giving clients time to migrate smoothly.

💡 Tips & Tricks

  • URI Versioning (Most Common): Embed the major version in the URL: /api/v1/users. This is the easiest for developers to see, test in a browser, and route at the API Gateway level.
  • Header Versioning (RESTful Purist): Send the version in the headers: Accept-Version: v1. This keeps the URL clean representing only the resource, but is harder to test via simple browser links.
  • Deprecation Headers: When phasing out an old version, respond with HTTP headers like Deprecation and Sunset to warn developers programmatically before turning the old API off entirely.
  • Only version breaking changes: Adding a new, optional field to a JSON response is not a breaking change. Don't bump the API version for backward-compatible additions.

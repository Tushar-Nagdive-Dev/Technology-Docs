The Circular Dependency

🚨 The Trap

Service A injects Service B. But Service B injects Service A. When Spring Boot starts, it tries to create A, realizes it needs B, tries to create B, realizes it needs A... and crashes with a BeanCurrentlyInCreationException.

@Service public class OrderService { @Autowired private PaymentService paymentService; } @Service public class PaymentService { @Autowired private OrderService orderService; }

✅ The Solution

Quick Fix: Use @Lazy on one of the dependencies. This tells Spring to inject a proxy initially, and only create the real bean when a method is actually called.

Architectural Fix (Best Practice): A circular dependency means your design is flawed. You should extract the shared logic into a third service (e.g., NotificationService) that both A and B can inject, or use Spring Application Events to decouple them entirely.

The N+1 Query Problem

🚨 The Trap

You fetch a list of 100 Author entities from the database (1 query). Then, in your code, you loop through them and call author.getBooks() to serialize them to JSON. Because the relationship is Lazy-loaded, Hibernate fires a separate query to fetch books for every single author (100 queries).

Result: 101 database queries just to load a single webpage. The app silently grinds to a halt in production.

✅ The Solution

Do not rely on lazy loading in loops. Tell the database to grab everything at once using a JOIN FETCH or an @EntityGraph.

// Solution 1: JPQL JOIN FETCH @Query("SELECT a FROM Author a JOIN FETCH a.books") List<Author> findAllWithBooks(); // Solution 2: EntityGraph (Cleaner) @EntityGraph(attributePaths = {"books"}) List<Author> findAll();
Pro Tip: Add spring.jpa.properties.hibernate.generate_statistics=true to your properties file during development. It will print exactly how many queries were fired for every API request!

Proxy Self-Invocation (The Ghost Annotation)

🚨 The Trap

Spring manages things like @Transactional, @Async, and @Cacheable by wrapping your classes in a "Proxy" (a middleman). If another class calls your method, it hits the proxy first, which starts the transaction.

BUT, if a method calls another method inside the same class, it bypasses the proxy entirely.

@Service public class UserService { public void registerUser() { // Calling a method in the SAME class... saveToDatabase(); } @Transactional // ❌ THIS IS IGNORED! public void saveToDatabase() { // DB logic here } }

✅ The Solution

Option 1 (Best): Move the @Transactional method to a different Service class, and inject that service into the current one.

Option 2: Autowire the service into itself! (Self-injection). This forces the call to go through the proxy.

@Service public class UserService { // Injecting myself to access my own proxy! @Autowired @Lazy private UserService self; public void registerUser() { self.saveToDatabase(); // ✅ TRANSACTION WORKS } }

Stateful Singletons (Data Bleeding)

🚨 The Trap

By default, Spring Beans (Controllers, Services) are Singletons. There is only ONE instance of the class shared across all users. If you declare a class-level variable (state) and modify it during a request, User B might see User A's data!

@RestController public class PaymentController { private String currentUserId; // ❌ FATAL MISTAKE! @PostMapping("/pay") public void processPayment(String userId) { this.currentUserId = userId; // Thread sleeps, another user calls /pay, currentUserId changes! chargeCard(this.currentUserId); // Charges the wrong person! } }

✅ The Solution

Rule of thumb: Never use mutable instance variables in Spring Beans. Keep them 100% stateless.

Pass data through method parameters (local variables), because local variables are stored on the thread stack and are naturally thread-safe.

@PostMapping("/pay") public void processPayment(String userId) { // ✅ local variable, safe for concurrent threads String safeUserId = userId; chargeCard(safeUserId); }

Lombok @Data on JPA Entities

🚨 The Trap

Putting Lombok's @Data annotation on a JPA Entity seems like a great way to save typing. However, @Data automatically generates a toString(), equals(), and hashCode() method that includes all fields.

If you have a Bidirectional relationship (User has Orders, Order has User), calling toString() will cause an infinite loop (StackOverflowError). Furthermore, relying on generated equals() for JPA entities breaks Set collections and detachment logic.

✅ The Solution

Never use @Data on JPA Entities. Be explicit instead.

Use @Getter and @Setter. If you absolutely need a toString(), use @ToString(exclude = "orders") to prevent infinite recursion.

// ❌ BAD @Entity @Data public class User { ... } // ✅ GOOD @Entity @Getter @Setter @NoArgsConstructor public class User { ... }

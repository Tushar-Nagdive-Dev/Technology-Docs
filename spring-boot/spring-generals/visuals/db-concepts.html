ACID Properties

The gold standard for reliable transactions

▼ Collapse

What is it?

ACID guarantees that database transactions are processed reliably. It stands for Atomicity (all or nothing), Consistency (valid state before & after), Isolation (concurrent transactions don't interfere), and Durability (committed data survives crashes). Think of it as a contract: the database promises your money transfer won't vanish halfway.

💣 Atomicity+ ✅ Consistency+ 🔒 Isolation+ 💾 Durability
PropertyMeaningReal-World Analogy
AtomicityAll steps succeed or all roll backWedding vows — you can't be "half married"
ConsistencyData respects all rules & constraintsChess — every move must leave a legal board
IsolationTransactions don't see each other's dirty workPrivate dressing room — no peeking
DurabilityOnce committed, it's permanentTattoo — it's not going away
💡 Pro Tip

Most Postgres and MySQL tables use ACID by default (InnoDB engine). If you're using MyISAM in MySQL, you lose ACID — switch to InnoDB immediately for production.

🎯 Trick: Partial Rollback with Savepoints

Use SAVEPOINT sp1; inside a transaction. If a later step fails, roll back to the savepoint — not the entire transaction. Great for batch processing with error recovery.

Indexes

Speed up reads, slow down writes — the classic trade-off

▶ Expand

What is it?

An index is a separate data structure (often a B+Tree) that maps column values to row locations. Like a book's index, it lets the database find rows without scanning every page. But every INSERT/UPDATE/DELETE must also update the index, which adds write overhead.

🔍 Query: WHERE email='x' → 📇 B+Tree Index → 📍 Row Pointer → 📄 Data Page
💡 Pro Tips
  • Use composite indexes for multi-column WHERE clauses — column order matters! (most selective first).
  • Monitor index bloat — unused indexes waste write performance and disk space. Use pg_stat_user_indexes in Postgres.
  • Partial indexes (e.g., WHERE active=true) are smaller and faster when filtering on a common condition.
🎯 Trick: Covering Index

Include all queried columns in the index (using INCLUDE clause in Postgres 11+). The database can answer the query from the index alone — no trip to the data page. Ultra-fast reads.

Primary Key vs Foreign Key

Relationships 101 — the backbone of relational databases

▶ Expand

The Simple Distinction

A Primary Key (PK) is a column (or set) that uniquely identifies each row in a table. A Foreign Key (FK) is a column in one table that references the Primary Key of another table — creating a link between them. PK enforces entity integrity; FK enforces referential integrity.

👤 users
id (PK) ← FK 📦 orders
user_id (FK)
💡 Pro Tips
  • Always use surrogate keys (auto-increment int or UUID) as PKs — never business data like email, which can change.
  • Define FKs with ON DELETE behavior explicitly: CASCADE, SET NULL, or RESTRICT. Don't rely on defaults.
🎯 Trick: Composite Foreign Keys

You can declare a FK on (user_id, tenant_id) that references a composite PK — this enforces multi-tenancy at the database level, preventing cross-tenant data leaks.

Normalization (All Forms)

Eliminate redundancy — 1NF through BCNF and beyond

▶ Expand

The Normal Forms (Simplified)

FormRule (in plain English)Problem It Solves
1NFEach cell holds a single value; no repeating groupsAtomicity of data
2NFNo partial dependency — non-key columns depend on the whole PKRemoves subset redundancy
3NFNo transitive dependency — non-key columns depend only on the PK, not on other non-key columnsEliminates derived data
BCNFEvery determinant is a candidate key (stricter 3NF)Handles edge cases 3NF misses

In practice, 3NF is the sweet spot for OLTP applications — it balances data integrity with query complexity. 4NF and 5NF are rarely needed outside academic contexts.

💡 Pro Tip

Normalize until it hurts, then denormalize until it works. Start with 3NF and only relax when you have proven performance bottlenecks.

SQL Joins: INNER, LEFT, RIGHT, FULL

Merging tables — know exactly what stays and what gets dropped

▶ Expand

Visualizing Joins

Imagine two circles (tables A and B) overlapping. Each join type picks different regions of the Venn diagram:

Join TypeReturnsWhen to Use
INNER JOINOnly rows with matches in both tablesConfirmed relationships (orders + users)
LEFT JOINAll rows from left table + matches from right; NULL if no match"All users, with orders if any"
RIGHT JOINAll rows from right table + matches from leftRare — rewrite as LEFT JOIN for clarity
FULL OUTER JOINAll rows from both tables; NULL where no matchFinding mismatches / data reconciliation
-- Classic LEFT JOIN example: all users & their latest order
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.created_at > '2026-01-01' OR o.id IS NULL;
🎯 Trick: Anti-Join with LEFT JOIN

Find rows in A not in B: LEFT JOIN B ON ... WHERE B.id IS NULL. Often faster than NOT IN or NOT EXISTS on large datasets — but always compare query plans.

Query Execution Plan (EXPLAIN ANALYZE)

Your best friend for debugging slow queries

▶ Expand

What is it?

EXPLAIN shows the plan the database will use. EXPLAIN ANALYZE actually runs the query and reports real timings, row counts, and loop iterations. It reveals whether the database is using an index, scanning the whole table (Seq Scan), or doing a nested loop vs. hash join.

-- Always run this before deploying a new query
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE user_id = 42 AND status = 'pending';
💡 Pro Tips
  • Look for Seq Scan on large tables — it's a red flag. Add an index or rewrite the query.
  • Compare estimated rows vs actual rows — a big mismatch means stale statistics; run ANALYZE.
  • In Postgres, use EXPLAIN (ANALYZE, BUFFERS) to see cache hit ratios.
🎯 Trick: Visualize with Online Tools

Paste your EXPLAIN output into explain.depesz.com or explain.dalibo.com — they highlight slow nodes in color, making bottlenecks instantly visible.

Connection Pooling

New connections kill performance — reuse them

▶ Expand

Why It Matters

Opening a database connection requires TCP handshake, SSL negotiation, and authentication — easily 10-50ms per connection. A connection pool keeps a set of persistent connections ready, lending them to requests and returning them when done. Without pooling, 1000 concurrent requests could overwhelm the database or exhaust memory.

🌐 App Server → 🏊 Pool (20 conns) → 🗄️ Database
💡 Pro Tips
  • Use PgBouncer (Postgres) or HikariCP (Java) — they're battle-tested and highly configurable.
  • Set max pool size to (core_count * 2) + effective_spindle_count as a starting rule of thumb.
  • Always configure connection timeouts and idle timeout to prevent stale connections.

Transaction Isolation Levels

Read Committed vs Serializable — how clean is your data?

▶ Expand

The Four Levels

LevelDirty ReadNon-Repeatable ReadPhantom ReadPerformance
Read Uncommitted✅ Yes✅✅Fastest
Read Committed ⭐❌ No✅✅Good (default in PG)
Repeatable Read❌❌✅Slower
Serializable❌❌❌Slowest (safest)

Read Committed is the practical default — it prevents dirty reads but allows non-repeatable reads. Use Serializable for financial transactions where absolute correctness trumps speed.

💡 Pro Tip

In Postgres, Repeatable Read actually prevents phantom reads too (unlike the SQL standard). If you're coming from MySQL, this is a key difference.

🎯 Trick: Optimistic Concurrency Control

Add a version column to your table. On UPDATE: SET version = version + 1 WHERE version = :oldVersion. If zero rows updated, retry. This avoids locks entirely for low-contention tables.

Denormalization

When breaking normalization rules actually helps

▶ Expand

What is it?

Denormalization intentionally adds redundant data to reduce the number of JOINs needed for queries. For example, storing user_name directly in the orders table avoids a JOIN to users on every order listing. The trade-off: write anomalies and extra storage for faster reads.

💡 Pro Tips
  • Denormalize only after you've measured a bottleneck — premature denormalization is tech debt.
  • Keep a single source of truth — update denormalized data via triggers, application code, or materialized views.
  • Common denormalization targets: counts (cached aggregate), names (avoiding JOIN), and JSON columns (flexible schema).
🎯 Trick: Materialized Views for Denormalization

Use Postgres materialized views to store pre-joined, pre-aggregated results. Refresh them with REFRESH MATERIALIZED VIEW CONCURRENTLY to avoid locking reads during refresh.

Partitioning vs Sharding

Horizontal scaling strategies — split data smartly

▶ Expand

The Key Difference

Partitioning splits a table into smaller pieces within the same database server. Sharding distributes data across multiple database servers (horizontal scaling). Partitioning is a single-server optimization; sharding is a distributed system strategy.

AspectPartitioningSharding
LocationSame DB serverMultiple DB servers
ComplexityLow — DB handles routingHigh — app or proxy handles routing
Cross-partition queriesSupported nativelyVery difficult / needs app logic
Use caseTime-series data, log archivingMassive scale (millions of users)
💡 Pro Tips
  • Start with partitioning (Postgres declarative partitioning). Only reach for sharding when a single server can't handle the load.
  • Choose partition key carefully — if most queries filter by tenant_id, partition by that.
  • Sharding by consistent hashing minimizes data movement when adding/removing nodes.

Replication

Keep copies in sync — high availability and read scaling

▶ Expand

What is it?

Replication copies data from a primary (leader) to one or more replicas (followers). Modes: synchronous (replica confirms before commit — zero data loss, slower) and asynchronous (fire-and-forget — faster, risk of lag). Replicas serve read queries, offloading the primary.

🖥️ Primary (Writes) → replicate → 📋 Replica 1 → 📋 Replica 2
💡 Pro Tips
  • Monitor replication lag — if a replica falls behind, users may see stale data. Alert when lag exceeds your SLA.
  • Use semi-synchronous replication for balance: wait for at least one replica to acknowledge, but don't block on all.
  • In Postgres, logical replication lets you replicate only specific tables — great for microservices sharing a DB.

CAP Theorem

You can only pick two — Consistency, Availability, Partition Tolerance

▶ Expand

The Inescapable Trade-off

In a distributed system, when a network partition occurs (servers can't talk to each other), you must choose between Consistency (all nodes see the same data at the same time) and Availability (every request receives a response). Partition Tolerance is non-negotiable — networks fail. So the real choice is: CP (consistent but may reject requests) or AP (always available but may return stale data).

🔒 Consistency / 📡 Partition Tolerance \ ✅ Availability
💡 Pro Tips
  • CP systems: Zookeeper, etcd, HBase. AP systems: Cassandra, DynamoDB, CouchDB.
  • Most relational databases in single-node mode are CA — but add replication and they shift toward CP or AP.
  • The PACELC theorem extends CAP: "if Partition, then Availability or Consistency; Else, Latency or Consistency."

Write-Ahead Logging (WAL)

The secret behind durability and crash recovery

▶ Expand

What is it?

WAL is a sequential log file where the database writes every change before modifying the actual data files. If the server crashes, the database replays the WAL to recover committed transactions and discard incomplete ones. This is how databases guarantee Durability in ACID — and it's also the foundation of replication and point-in-time recovery (PITR).

✍️ Write → 📝 WAL (sequential append) → 💾 Data Files (lazy write)
💡 Pro Tips
  • Put the WAL on a separate, fast disk (NVMe) — sequential writes benefit from low latency.
  • Configure WAL segment size and checkpoint intervals carefully — frequent checkpoints reduce recovery time but increase I/O.
  • Use WAL archiving for continuous backup: ship WAL files to S3 for point-in-time recovery up to the second.

Database Locking

The invisible gatekeeper — concurrency control under the hood

▶ Expand

Types of Locks

Lock TypeGranularityConflict Behavior
Shared Lock (S)Row / TableAllows other S locks; blocks X locks
Exclusive Lock (X)Row / TableBlocks all other locks
Row-Level LockSingle rowHigh concurrency — Postgres default for DML
Table-Level LockEntire tableLow concurrency — DDL, bulk operations
DeadlockN/ATwo transactions waiting on each other → one gets killed
💡 Pro Tips
  • Always access tables in the same order across transactions to prevent deadlocks.
  • Use SELECT ... FOR UPDATE to lock rows for a subsequent update — prevents lost updates in high-concurrency scenarios.
  • Monitor lock contention with pg_stat_activity (Postgres) or SHOW ENGINE INNODB STATUS (MySQL).
🎯 Trick: Advisory Locks for Application Coordination

Postgres advisory locks (pg_advisory_lock) let you use the database as a distributed mutex. Perfect for ensuring only one worker processes a given batch — without locking any real data.

CQRS: Separate Read & Write Models

Query one database, command another — optimize both

▶ Expand

What is CQRS in Databases?

Command Query Responsibility Segregation splits the data layer into a write model (optimized for transactional integrity, normalized) and a read model (optimized for queries, denormalized, often in a different database — e.g., Elasticsearch or a read replica). This decouples the performance characteristics of reads and writes.

✍️ Command (Write) → 🗄️ Primary DB (normalized) → event → 📖 Read DB (denormalized) ← 👀 Query (Read)
💡 Pro Tips
  • Sync the read model asynchronously via change data capture (CDC) or event-driven messaging — expect eventual consistency.
  • The read model can be a completely different technology: Elasticsearch for full-text search, Redis for leaderboards, or a simple Postgres replica with different indexes.
  • Not every feature needs CQRS — apply it only where read/write patterns diverge significantly.
🎯 Trick: CQRS Lite with Database Views

Start simple: create database views or materialized views tailored for specific queries. This gives you logical separation without the operational overhead of dual databases — upgrade to full CQRS only when necessary.

Top 5 Best Practices for Securing Spring Boot APIs

An in-depth guide with concepts, real-world scenarios, and implementation code.

1. Implement Stateless Authentication (JWT & OAuth2)

Deep Dive: Traditional web applications use server-side sessions (JSESSIONID) to remember logged-in users. In a modern API ecosystem, this is a bottleneck. It requires servers to share session state (which is hard to scale) and leaves APIs vulnerable to Cross-Site Request Forgery (CSRF). The best practice is stateless authentication using JSON Web Tokens (JWT). The server issues a cryptographically signed token, and the client sends this token in the Authorization header with every request. The server verifies the math behind the signature rather than looking up a session in a database.

Real-Time Scenario: Imagine a Ride-sharing app. A user’s app connects to a gateway, which routes traffic to 50 different microservices (Billing, Location, Matching). If the system used sessions, all 50 services would need to constantly check a centralized Redis cache to see if the user is logged in. With a JWT, any microservice can instantly verify the user's identity just by reading the token's signature.

Spring Boot Implementation:

You must configure your API to reject sessions and disable CSRF (since stateless APIs are immune to CSRF if tokens are handled correctly by the client).

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            // 1. Disable CSRF (safe because we don't use cookies/sessions)
            .csrf(csrf -> csrf.disable())
            
            // 2. Make the application strictly stateless
            .sessionManagement(session -> 
                session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            
            // 3. Define authorization rules
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/login").permitAll()
                .anyRequest().authenticated()
            )
            
            // 4. Tell Spring to look for and validate JWTs in the Authorization header
            .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()));
        
        return http.build();
    }
}

2. Enforce Object-Level Authorization (Prevent BOLA/IDOR)

Deep Dive: Broken Object Level Authorization (BOLA), also known as IDOR, is the #1 API vulnerability in the world. It happens when your API checks if a user is logged in, but fails to check if that specific user owns the data they are requesting.

Real-Time Scenario: Consider a Banking API. User Alice logs in and her app requests her account details via GET /api/accounts/1001. A hacker sees this URL pattern, logs into their own account (so they have a valid JWT), and changes the URL to GET /api/accounts/1002. If the API only checks "Is this user authenticated?", it will gladly return User Bob's bank details to the hacker.

Spring Boot Implementation:

Never rely purely on URL paths. Use Method Security with Spring Expression Language (SpEL) to ensure the ID in the URL matches the ID of the logged-in user.

// 1. Enable Method Security
@Configuration
@EnableMethodSecurity
public class MethodSecurityConfig { }

// 2. Controller Implementation
@RestController
@RequestMapping("/api/accounts")
public class AccountController {

    // 3. The magic happens here. We call a custom security bean to check ownership.
    @GetMapping("/{accountId}")
    @PreAuthorize("@securityChecker.isAccountOwner(authentication, #accountId)")
    public ResponseEntity<AccountDTO> getAccountDetails(@PathVariable Long accountId) {
        return ResponseEntity.ok(accountService.getAccount(accountId));
    }
}

// 4. Custom Security Component
@Component("securityChecker")
public class SecurityChecker {
    
    public boolean isAccountOwner(Authentication authentication, Long requestedAccountId) {
        // Extract the user ID from the JWT token
        Jwt jwt = (Jwt) authentication.getPrincipal();
        Long loggedInUserId = jwt.getClaim("userId");
        
        // Check the database: Does this account actually belong to this user?
        return databaseService.verifyOwnership(loggedInUserId, requestedAccountId);
    }
}

3. Strict Input Validation & Mass Assignment Protection

Deep Dive: APIs should never blindly trust data sent by the client. Mass Assignment occurs when an API binds a JSON payload directly to a database Entity. Attackers can inject fields into the JSON that the developer didn't intend to be updated. The fix is to always use Data Transfer Objects (DTOs) and apply strict jakarta.validation annotations.

Real-Time Scenario: In an E-commerce app, a regular user updates their profile using PUT /api/users/me with {"firstName": "John"}. A hacker intercepts this and sends {"firstName": "Hacker", "role": "ADMIN", "walletBalance": 99999}. If the API maps this directly to the User JPA entity and saves it, the hacker just gave themselves admin rights and free money.

Spring Boot Implementation:

// 1. Create a DTO that ONLY contains allowed fields. 
// No 'role' or 'walletBalance' fields exist here.
public class ProfileUpdateDTO {
    
    @NotBlank(message = "First name is required")
    @Size(min = 2, max = 50)
    // Regex prevents malicious script injection (XSS)
    @Pattern(regexp = "^[a-zA-Z]+$", message = "Only letters allowed")
    private String firstName;

    // getters and setters...
}

// 2. Controller forces validation
@RestController
@RequestMapping("/api/users")
public class UserController {

    @PutMapping("/me")
    // The @Valid annotation triggers the rules defined in the DTO
    public ResponseEntity<String> updateProfile(@Valid @RequestBody ProfileUpdateDTO dto) {
        
        // Safe: We only extract exactly what we allowed in the DTO
        userService.updateFirstName(dto.getFirstName());
        
        return ResponseEntity.ok("Profile updated safely");
    }
}

4. Implement Rate Limiting

Deep Dive: Your API needs a shield against brute-force attacks, credential stuffing (hackers using leaked passwords from other sites), and basic DDoS attacks. Rate limiting restricts how many requests a single IP or API Key can make within a specific timeframe using algorithms like the "Token Bucket."

Real-Time Scenario: During a Ticketmaster ticket drop, thousands of malicious bots try to hit the /api/checkout endpoint simultaneously to scalp tickets. Without rate limiting, the database crashes. With rate limiting (e.g., 2 requests per second per IP), the bots are instantly rejected with an HTTP 429 Too Many Requests status, keeping the servers online for real users.

Spring Boot Implementation:

You can use the open-source Bucket4j library implemented as a Servlet Filter.

@Component
public class RateLimitingFilter extends OncePerRequestFilter {

    // Allow 10 requests per minute
    private final Bucket bucket = Bucket.builder()
            .addLimit(Bandwidth.classic(10, Refill.intervally(10, Duration.ofMinutes(1))))
            .build();

    @Override
    protected void doFilterInternal(HttpServletRequest request, 
                                    HttpServletResponse response, 
                                    FilterChain filterChain) throws ServletException, IOException {
        
        // Apply limit only to sensitive endpoints like login
        if (request.getRequestURI().startsWith("/api/auth/login")) {
            if (bucket.tryConsume(1)) {
                filterChain.doFilter(request, response); // Token consumed, allow request
            } else {
                // Bucket is empty, reject request
                response.setStatus(HttpStatus.TOO_MANY_REQUESTS.value());
                response.getWriter().write("Too many attempts. Please wait 1 minute.");
                return;
            }
        } else {
            filterChain.doFilter(request, response);
        }
    }
}

5. Secure the Transport Layer and Headers

Deep Dive: Even if your API logic is flawless, data in transit is vulnerable. You must force HTTPS (TLS 1.2 or 1.3) so data cannot be intercepted. Furthermore, APIs accessed by browsers must return hardened HTTP Security Headers to prevent the browser from executing malicious scripts (XSS) or being tricked into rendering the API inside an invisible iframe (Clickjacking).

Real-Time Scenario: A user logs into their Crypto Portfolio API while on public airport Wi-Fi. If the API allows unencrypted HTTP connections, a hacker sitting across the terminal can use packet sniffing tools to grab the user's JWT token right out of the air. Enforcing Strict-Transport-Security (HSTS) guarantees the connection is locked down.

Spring Boot Implementation:

You can enforce this globally in your SecurityFilterChain.

@Bean
public SecurityFilterChain secureHeadersChain(HttpSecurity http) throws Exception {
    http
        // 1. Force all requests to use HTTPS
        .requiresChannel(channel -> channel.anyRequest().requiresSecure())
        
        // 2. Inject Security Headers
        .headers(headers -> headers
            // Force browsers to remember this site is HTTPS-only for 1 year (HSTS)
            .httpStrictTransportSecurity(hsts -> hsts
                .includeSubDomains(true)
                .maxAgeInSeconds(31536000) 
            )
            // Prevent Clickjacking
            .frameOptions(frame -> frame.deny())
            // Prevent browsers from guessing the file type
            .contentTypeOptions(Customizer.withDefaults())
            // Strict Content Security Policy
            .contentSecurityPolicy(csp -> csp
                .policyDirectives("default-src 'none'; frame-ancestors 'none'")
            )
        );
        
    return http.build();
}

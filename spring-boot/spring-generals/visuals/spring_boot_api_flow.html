🔗 Step 0: The Servlet Filter Chain (the missing piece)

Before any Spring MVC logic runs, the request passes through a chain of filters. Filters are part of the Java Servlet specification, not Spring-specific. They can modify the request/response, perform authentication, log headers, compress data, or even abort the request early. Spring Security heavily relies on this.

📌 Critical point: The filter chain wraps the entire Spring MVC processing. Filters are invoked before the DispatcherServlet and after the servlet returns (in reverse order). This allows cross-cutting concerns like authentication, CORS, rate limiting, and request wrapping.

🧩 Complete Step-by-Step Internal Flow

Let's trace a GET /api/users/5 request with a hypothetical @RestController.

1 Request arrives at Servlet Container (Tomcat)

Tomcat accepts the TCP connection, parses HTTP protocol, creates HttpServletRequest and HttpServletResponse objects. It then locates the appropriate servlet based on the URL mapping – in Spring Boot, the DispatcherServlet is mapped to / (all requests).

2 Servlet Filter Chain is executed (before servlet)

Tomcat calls doFilter() on the first filter in the chain. Each filter can:

  • Examine/modify request – e.g., add custom headers, validate JWT token
  • Short-circuit – respond directly (e.g., return 401 Unauthorized) without invoking subsequent filters or the servlet
  • Wrap request/response – e.g., use caching, compression
  • Pass to next filter via chain.doFilter(request, response)

Spring Security registers a single DelegatingFilterProxy that then invokes the security filter chain (authentication, authorization, CSRF, etc.). After all filters approve, the call reaches the DispatcherServlet.

// Example custom filter public class LoggingFilter implements Filter { public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) { System.out.println("Request received at " + new Date()); chain.doFilter(req, res); // pass to next filter or servlet System.out.println("Response sent back"); } }
3 DispatcherServlet starts processing

DispatcherServlet is the front controller. It receives the request and begins orchestrating the Spring MVC workflow: identifies the handler (controller method), executes it, and renders the response.

4 HandlerMapping finds the right controller method

RequestMappingHandlerMapping matches the request URI (/api/users/5) and HTTP method (GET) against all @RequestMapping annotations. It extracts path variables (id=5) and returns a HandlerExecutionChain (handler + interceptors).

5 HandlerAdapter executes the controller method

RequestMappingHandlerAdapter invokes the method. Before invocation, it resolves method parameters using HandlerMethodArgumentResolver (e.g., converting @PathVariable to Long). After method execution, it processes the return value via HandlerMethodReturnValueHandler.

6 The controller method runs (your business logic)

Your @GetMapping method executes, perhaps calling a service layer or database. It returns a domain object (e.g., User) or ResponseEntity.

7 HttpMessageConverter serializes the response

The HandlerAdapter selects a HttpMessageConverter (usually MappingJackson2HttpMessageConverter) based on the Accept header. It converts the returned object into JSON (or XML) bytes and writes them to the HttpServletResponse output stream.

8 DispatcherServlet completes, returns control to filter chain

After the servlet finishes, the response travels back through the filter chain in reverse order. Filters can modify the response (e.g., add headers, compress output). Finally, Tomcat sends the raw HTTP response back to the client.

⚡ How Spring Boot integrates filters

Spring Boot automatically registers many filters:

  • CharacterEncodingFilter – sets character encoding (UTF-8)
  • HiddenHttpMethodFilter – enables _method parameter for PUT/DELETE in forms
  • FormContentFilter – reads form data for PUT/PATCH requests
  • RequestContextFilter – exposes Spring request context
  • Spring Security Filter Chain – only if spring-boot-starter-security is present

You can register custom filters as @Bean of type Filter or OncePerRequestFilter. Spring Boot automatically adds them to the chain with proper ordering (using @Order or FilterRegistrationBean).

@Bean public Filter tenantFilter() { return (request, response, chain) -> { String tenant = request.getHeader("X-Tenant-ID"); TenantContext.set(tenant); chain.doFilter(request, response); TenantContext.clear(); }; }

🔍 Filter vs. Spring Interceptor – what's the difference?

Servlet Filter
Part of Java Servlet API. Works for any servlet, not only Spring. Can wrap request/response. Executes before DispatcherServlet (and after).
Spring HandlerInterceptor
Spring-specific. Executes after DispatcherServlet finds handler but before method call, and after view resolution (or JSON write). Has preHandle, postHandle, afterCompletion.
Use case example
Filter: authentication, logging, compression. Interceptor: adding common model attributes, auditing controller metrics.
Many developers confuse filters and interceptors. Filters sit outside Spring MVC; Interceptors are inside the DispatcherServlet's handler execution chain. Filters are more powerful but less "Spring-aware".

🏭 Production impact: why you must understand the filter chain

  • Performance: Heavy filters (e.g., authentication with database lookup) affect every request. Order matters – place lightweight filters first.
  • Debugging: If a request never reaches your controller, a filter might have short‑circuited it (e.g., invalid token).
  • Request/response modification: Need to add a correlation ID? That's a filter. Want to log request bodies? Wrap the request with a ContentCachingRequestWrapper in a filter.
  • Security: Spring Security's filter chain is the cornerstone of authentication and authorization – it runs entirely within the filter chain.

📝 Realistic end-to-end example

// 1. Custom filter that checks API key @Component public class ApiKeyFilter implements Filter { @Override public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) throws IOException, ServletException { HttpServletRequest request = (HttpServletRequest) req; String apiKey = request.getHeader("X-API-Key"); if (!"secret".equals(apiKey)) { ((HttpServletResponse) res).sendError(401, "Invalid API Key"); return; // short-circuit, never reaches DispatcherServlet } chain.doFilter(req, res); // proceed to next filter → DispatcherServlet } } // 2. Controller @RestController @RequestMapping("/api") public class DataController { @GetMapping("/data") public Map getData() { return Map.of("message", "Sensitive data"); } } // Flow: Request → ApiKeyFilter (validates) → (if valid) DispatcherServlet → HandlerMapping → Controller → MessageConverter → Response goes back through filter → client.
🧠 Final mental model: The filter chain is like a series of security checkpoints and processing stations before a request reaches the main office (DispatcherServlet). Inside the office, Spring MVC does its routing and response building. After leaving the office, the request goes back through the same checkpoints in reverse order. This design gives you complete control over the HTTP pipeline.

What really happens when you send a HTTP request to a `@RestController`? From the network socket to the JSON response – a simple yet deep look inside the magic.

🧭 The Big Picture

Spring Boot hides incredible complexity behind a few annotations like @RestController and @GetMapping. Under the hood, a chain of smart components transforms an HTTP request into a Java method call and then serializes the returned object into a response (JSON, XML, etc.). All of this happens synchronously inside the servlet container (Tomcat by default).

🔬 Step‑by‑Step Internal Flow (simple terms)

Let's follow a real example: a client sends GET http://localhost:8080/api/orders/42 and we have a Spring Boot controller with @GetMapping("/api/orders/{id}") that returns an Order object (converted to JSON).

1 Request arrives at the servlet container (Tomcat)

Tomcat (or Jetty/Undertow) listens on port 8080. It receives the raw HTTP request, wraps it into HttpServletRequest and HttpServletResponse objects, and delegates to the Spring DispatcherServlet – the front controller configured by Spring Boot auto‑configuration.

2 DispatcherServlet asks: "Which controller can handle this?" → HandlerMapping

DispatcherServlet consults one or more HandlerMapping implementations. They map incoming requests to handler objects (usually @Controller methods). For REST APIs, RequestMappingHandlerMapping scans all @RequestMapping annotations and builds a lookup table. It matches the HTTP method (GET), URL pattern (/api/orders/42) and extracts the path variable id=42.

// Under the hood: The mapping registry stores method metadata // HandlerMapping returns a HandlerExecutionChain (handler + interceptors)
3 DispatcherServlet finds a HandlerAdapter that can execute the handler

Not every handler can be called directly. Spring uses HandlerAdapter to invoke the handler method in a uniform way. For annotated controllers, the RequestMappingHandlerAdapter is the perfect match. It knows how to resolve method parameters, convert arguments, and handle the return value.

4 Argument resolvers prepare method parameters

Before invoking the controller method, Spring resolves all parameters: @PathVariable, @RequestParam, @RequestBody, @ModelAttribute, or even native HttpServletRequest. For our example, it:

  • Reads id from the URI template → converts "42" to Long (using ConversionService)
  • If there were query parameters or JSON body, special resolvers (like RequestResponseBodyMethodProcessor) would deserialize the body using HttpMessageConverter.
💡 Note: For GET requests without a request body, no deserialization is needed – only path/query parameters.
5 Controller method executes → business logic

Finally, the actual method on the @RestController is invoked. It runs your code (service call, DB query, etc.) and returns a domain object (e.g., Order object) or a ResponseEntity.

@RestController public class OrderController { @GetMapping("/api/orders/{id}") public Order getOrder(@PathVariable Long id) { return orderService.findById(id); // returns Order instance } }
6 Return value handling: HttpMessageConverter writes the response body

The HandlerAdapter uses HandlerMethodReturnValueHandler to process the returned object. For @ResponseBody (implicit in @RestController), it selects an appropriate HttpMessageConverter based on:

  • The Accept header sent by client (e.g. application/json)
  • The available converters (Jackson2 for JSON, Jaxb2 for XML, etc.)

Jackson's MappingJackson2HttpMessageConverter serializes the Order object into JSON bytes. Also sets Content-Type: application/json.

7 DispatcherServlet writes the response and commits it

The servlet writes the serialized JSON to the HttpServletResponse output stream, sets the HTTP status code (200 OK by default). The container sends the final HTTP response back to the client. The request is complete.

📌 Key Spring MVC components (in plain english)

🔹 DispatcherServlet
Front controller – central orchestrator. Receives every request, delegates to mappings, adapters, and returns response.
🔹 HandlerMapping
Maps HTTP request to handler method (based on URL, HTTP method, headers).
🔹 HandlerAdapter
Invokes the controller method, manages argument resolvers and return value handlers. Decouples DispatcherServlet from controller signatures.
🔹 HandlerMethodArgumentResolver
Extracts & converts request data into method parameters (@PathVariable, @RequestParam, @RequestBody).
🔹 HttpMessageConverter
Converts HTTP request body to Java objects (deserialization) and Java objects to HTTP response body (serialization). JSON, XML, etc.
🔹 ReturnValueHandler
Processes the object returned from controller: wraps with response status, uses message converter, or handles ResponseEntity.

⚠️ What about errors & exceptions?

If the controller throws an exception (e.g., ProductNotFoundException), the HandlerAdapter doesn't immediately crash. Instead, it propagates the exception up to the DispatcherServlet, which delegates to registered HandlerExceptionResolver components. The @ExceptionHandler methods inside @RestControllerAdvice are invoked, allowing you to return a custom error JSON body with proper HTTP status (404 etc.).

🧠 Key takeaway: The whole chain is designed to be modular and pluggable – you can inject custom interceptors, converters, argument resolvers, or error handlers without changing the core flow.

🧩 Simple analogy: Restaurant Order

  • Waiter = DispatcherServlet (receives your request, coordinates everything)
  • Host/Manager with seating map = HandlerMapping (finds which waiter/chef handles your dish)
  • Chef's assistant = HandlerAdapter (adapts order to specific chef and prepares ingredients)
  • Chef = Controller method (cooks the meal / executes business logic)
  • Plating & garnish = HttpMessageConverter (converts the meal into presentable JSON format)
  • Final delivery = HTTP Response back to customer

Everything flows in a single organized pipeline — that’s Spring MVC under the hood.

✨ Spring Boot's extra magic (auto-configuration)

When you add spring-boot-starter-web, Spring Boot automatically:

  • ✅ Configures DispatcherServlet and registers it with Tomcat
  • ✅ Enables RequestMappingHandlerMapping, RequestMappingHandlerAdapter
  • ✅ Registers Jackson HttpMessageConverter if Jackson is on classpath
  • ✅ Provides default exception handling with BasicErrorController

This is why you can start a REST API with zero XML and just a few annotations.

❓ Common questions (deep clarity)

🔸 Does every request create a new controller instance?

No. By default, controllers are singletons (shared across all requests). They are thread‑safe if you avoid storing mutable state. Spring reuses the same controller bean for all matching requests.

🔸 How does Spring know to convert JSON body to Java object?

The @RequestBody parameter triggers RequestResponseBodyMethodProcessor (an argument resolver). It reads the request body and selects a matching HttpMessageConverter (e.g., MappingJackson2HttpMessageConverter) based on the Content-Type header.

🔸 What if the controller returns ResponseEntity?

ResponseEntity gives you full control over status, headers, and body. The return value handler (HttpEntityMethodProcessor) picks it up, extracts status/headers, and then uses the body with a message converter — still the same underlying flow.

🧪 Summary in one sentence: The DispatcherServlet receives the request, asks HandlerMapping which controller method to call, uses HandlerAdapter to invoke it with resolved arguments, then converts the returned object into an HTTP response using message converters.
🧠 Understanding the internal flow of Spring Boot REST APIs empowers you to debug effectively, write custom interceptors, and extend the framework with confidence. Every request follows this elegant pipeline — from HTTP to your @RestController and back.

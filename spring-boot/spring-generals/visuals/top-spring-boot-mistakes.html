🚨 Spring Boot: Top 10 Silent Production Killers

1 ddl-auto=update in Production

The Problem: Using spring.jpa.hibernate.ddl-auto=update allows Hibernate to automatically alter your database schema on startup. In production, this can accidentally lock massive tables, drop crucial constraints, or fail silently midway through, taking down your entire database. It is highly unpredictable.
🔧 The Fix: Set it to validate or none in production. Use proper database migration tools like Flyway or Liquibase to version control and safely apply schema changes.

2 No Read Timeouts on HTTP Clients

The Problem: When calling an external API (using RestTemplate, WebClient, or Feign), if you don't set a timeout and the external server hangs, your application's thread hangs with it. If 200 users hit that endpoint, 200 of your threads will wait indefinitely. This exhausts your thread pool, and your app crashes (Thread Starvation).
🔧 The Fix: Always set explicit timeouts. Connection Timeout (e.g., 3s), Read Timeout (e.g., 5s), and Connection Request Timeout (e.g., 2s). Treat all external systems as if they might fail at any moment.

3 @Transactional on Private Methods

The Problem: Spring uses "proxies" (wrappers) around your beans to magically handle transactions, caching, and async logic. However, these proxies only intercept calls coming from outside the class. If you put @Transactional on a private method (or call it from another method within the same class), the proxy is bypassed. The transaction simply never starts, leading to incomplete data saves if an error occurs.
🔧 The Fix: Only apply @Transactional, @Async, @Cacheable, and @Retryable to public methods, and ensure they are called from another bean/class.

4 Returning Entities Directly from Controllers

The Problem: Returning JPA Entities (like a User class) directly as JSON is a recipe for disaster. It couples your database design directly to your API contract. Worse, it often causes Infinite Recursion (e.g., User has Orders, Order has User... leading to a StackOverflow) and can accidentally leak sensitive data like password hashes to the frontend.
🔧 The Fix: Always use DTOs (Data Transfer Objects). Map your Entity to a DTO (using tools like MapStruct or manual mapping) and only return exactly what the client needs.

5 Default HikariCP Pool + Long Transactions

The Problem: HikariCP is the default, incredibly fast connection pool in Spring Boot, but its default max pool size is only 10. If you wrap a long-running process (like making a slow HTTP call to a 3rd party API or processing a huge file) inside a @Transactional block, you hold onto a database connection for that entire time. Just 10 concurrent users can exhaust the pool, causing the whole app to freeze for everyone else.
🔧 The Fix: Keep transactions as short as possible. Fetch data, close the transaction, do the heavy/slow non-DB work, and open a new transaction only when it's time to save.

6 The N+1 Query Problem

The Problem: You fetch a list of 100 Authors (1 query). Your code then loops through them to get their Books. Because of lazy loading, Hibernate executes a separate query for each author's books (100 queries). You just executed 101 queries to load a single page. It works fine in dev with 3 rows, but silently kills server performance in production.
🔧 The Fix: Use JOIN FETCH in your JPQL queries, or use Spring Data JPA @EntityGraph to fetch the related entities in a single, optimized SQL query.

7 Exposing All Actuator Endpoints

The Problem: Spring Boot Actuator provides amazing metrics, but if you set management.endpoints.web.exposure.include=* without security, you've just handed hackers the keys to the kingdom. Endpoints like /actuator/env can expose AWS keys or database passwords, and /actuator/heapdump can let attackers download your server's entire RAM memory.
🔧 The Fix: Only expose health and info publicly. If you need other endpoints, secure the /actuator/** path behind Spring Security so only admins can access them.

8 Using findAll() Without Pagination

The Problem: Writing repository.findAll() seems harmless. But over time, as your table grows to millions of rows, fetching all of them at once will load the entire dataset into your JVM memory. This causes an immediate OutOfMemoryError (OOM), crashing your application pod instantly.
🔧 The Fix: Never use plain findAll() on large tables. Always use Spring Data's Pageable or Slice to process data in manageable chunks.

9 Field Injection (@Autowired on Variables)

The Problem: Using @Autowired directly on private fields allows you to easily create circular dependencies (A depends on B, B depends on A) that Spring will try to magically resolve, leading to fragile startup sequences. It also makes writing unit tests incredibly annoying, as you have to use reflection to inject mocks.
🔧 The Fix: Use Constructor Injection. Make your dependencies final. (Pro-tip: Use Lombok's @RequiredArgsConstructor to generate the constructor automatically, keeping your code clean and enforcing immutability).

10 Ignoring Graceful Shutdown

The Problem: When deploying a new version to Kubernetes or Docker, the orchestration tool sends a kill signal to your old container. By default, Spring Boot shuts down instantly, dropping any HTTP requests or database transactions that were currently in progress. Users get random 500 errors or corrupted data during deployments.
🔧 The Fix: Add server.shutdown=graceful to your properties. This tells Spring Boot to stop accepting new requests, but wait a few seconds (configurable) for currently processing requests to finish before pulling the plug.
